# go-fund-operations

开放式基金交易与估值服务的 Go 项目基础模块。

开发环境：Go 1.23.0。

运行测试：

    go test ./...

## liquidation：基金终止清算分配

`liquidation` 包实现基金终止后的清算分配全流程：清算方案、份额快照、
首笔分配、准备金释放形成的补充分配、可恢复的付款执行与并发安全的状态流转。

### 核心概念

- **清算方案（Plan）**：固定基金、登记日、可分配现金、费用准备金、
  争议准备金和份额快照。方案确认（`Confirm`）后冻结份额、停止新的份额交易；
  登记日之后的持仓变化不得进入本次清算（`CheckTradeAllowed`）。
- **份额快照（Snapshot）**：登记日各投资者的冻结份额，首笔与全部补充分配
  均按该快照计算，后续持仓变化不影响本次清算。
- **分配批次（Batch）**：一次分配运行。首笔批次来自可分配现金
  （总资产 − 费用准备金 − 争议准备金）；补充分配批次来自准备金释放
  （`ReleaseReserve`），仍按原冻结份额分配。
- **分配明细（Item）**：每名投资者在一个批次中的应付金额与状态
  （`PENDING` / `PAID` / `ON_HOLD`）。

### 确定性与守恒

- 金额以最小货币单位（分）的整数表示；分配规则为
  `floor(总额 × 冻结份额 / 总份额)`，使用 `big.Int` 计算，避免溢出，
  结果完全确定；余数形成尾差（dust）留存在清算资产中。
- 不变式：全部分配 + 未释放准备金 + 尾差 = 清算资产总额，
  由 `Plan.Reconcile` 校验。

### 执行与恢复

- `ExecuteBatch` 扫描批次并逐笔付款；付款网关（`PaymentGateway`）
  按 (批次, 投资者) 幂等。
- 扫描中断后重试只补齐 `PENDING` 明细，已付款明细不会重复付款。
- 已退出或账户状态异常的投资者不会被静默跳过，而是进入 `ON_HOLD`
  待处理状态并记录原因，批次置为 `PARTIAL`。
- 方案取消、付款确认（`ConfirmPayment`）、准备金释放并发时由服务级
  互斥锁串行化，保证唯一结果：已有付款的方案不可取消，已取消的方案
  不可再付款或释放准备金。

### 查询接口

- `GetPlan`：清算方案；`GetSnapshot`：份额快照；
- `ListBatches`：分配批次；`PaymentProgress`：付款进度；
- `RemainingAssets`：剩余资产（未释放准备金 + 未付明细 + 尾差）。

### 测试

    go test ./liquidation/ -race -count=1

覆盖：舍入确定性与总额守恒、登记日快照冻结、中断恢复不重复付款、
补充分配与待处理状态、取消/付款确认/准备金释放并发竞态、查询接口。
